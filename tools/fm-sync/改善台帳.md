## 方針転換（2026-09-10 決定）

**FileMaker を直すのをやめ、Hub を FileMaker の「別の窓口」にする。**

本多さんの指示:

> 一旦 tokiwahub にファイルメーカーの受注入力画面をそのままのせる。見積書画面もとりあえず、
> 同じにする。その他機能は見え方は違うが同じことができるようにする。
> 従ってファイルメーカーを修正ではなく、ファイルメーカーのデータをリアルタイムな状態で
> tokiwahub にうつしていき、トキワハブでも使えるようにする。機能的には tokiwahub の方が
> 容易にアップデートできるため、使いながら更新をしていき、結果、ファイルメーカーを
> 使いながら徐々に tokiwahub に移管していく。

理由は今日の実作業で出た。FileMaker はレイアウト1つ直すのに半日かかり、事故も起きる。
Hub なら git で戻せて、直したその日に使える。

### かたち

```
Hub（ブラウザ）  →  GAS 中継（更新トークンを保管）  →  FileMaker Cloud Data API  →  トキワ印刷DB
```

**データベースを二重に持たない。** FileMaker が唯一の正データのまま、Hub は窓口になる。
同期しないので、同期ズレも二重更新の衝突も起きない。

### 実測で確かめたこと（2026-09-10）

**① SRP なしでトークンが取れる**

保存済みの更新トークンを Cognito に素の HTTPS で投げるだけで、1時間有効な ID トークンが返る。
それで Data API のセッションも張れた。**つまり GAS から直接 FileMaker を叩ける。**

```
POST https://cognito-idp.us-west-2.amazonaws.com/
X-Amz-Target: AWSCognitoIdentityProviderService.InitiateAuth
{"AuthFlow":"REFRESH_TOKEN_AUTH","ClientId":"4l9rvl4mv5es1eep1qe97cautn",
 "AuthParameters":{"REFRESH_TOKEN":"..."}}
→ AuthenticationResult.IdToken（1294文字・3600秒）
```

**② 受注入力に必要な FileMaker の列は 262**

`tools/fm-juchu.html` の `FMUSE`（Hub項目 ⇄ FM列名の対応表・308件）から確定。

| | 件数 | 意味 |
|---|---|---|
| normal | 113 | 書き込める |
| calculation | 42 | 読むだけ。金額系（用紙代・印刷代・合計金額…） |
| `受注データ` レイアウトに無い | 107 | テーブルにはあるが、あのレイアウトに載っていないだけ |

一覧は `tools/fm-sync/hub受注_必要列.txt`。

**金額の計算式を Hub 側で作り直す必要はない。** 入力値を書き込めば FileMaker が計算し、
それを読み返せばよい。二重実装による食い違いが原理的に起きない。

**③ レイアウトの重さ**

| レイアウト | 項目 | うち計算 | 1件の取得 |
|---|---|---|---|
| `Hub連携` | 73 | 12 | 0.36秒 |
| `受注データ` | 378 | 78 | 120秒でも返らない |

**計算フィールドの数が効いている。** 今回は 262項目・計算42。
まず1枚で作って計測し、遅ければ「入力用（normal）」と「金額用（calculation）」に割る。

### 画面の置き場所（2026-09-10 決定）

本多さんの指示:

> この画面をファイルメーカーの画面にしていき、実装していきたい
> （Hub の 案件管理→入力 を見ながら）
> 1（見た目を FileMaker そっくりに作り替える）＋データもファイルメーカーと同じにしていきたい
> hub に導入したいけどどう？ それでどこかのタイミングで連携を外す

**最終形は Hub 単独。** FileMaker との連携は途中の足場であって、目的ではない。
だから画面は Hub（GitHub Pages）に置き、中継の呼び方だけを差し替えられる形にする。

```
tools/fm-juchu.html           元の画面（写し。ここだけを直す）
  └ build_juchu.py で組み立て
      ├ tools/fm-relay/juchu.html   Apps Script が配る版（google.script.run）
      └ tools/fm-juchu-hub.html     Hub に置く版（fetch + Google サインイン）
```

呼び口は `window.FM呼ぶ(名前, 引数)` の1か所に閉じてある。
**FileMaker との連携を外すときは、ここを Hub 自身のデータに向けるだけ**で、
画面も操作も変えなくてよい。

#### なぜ OAuth クライアントID が要るのか

Apps Script が配る版は、ページ自体が社内アカウントでしか開けないので、
`Session.getActiveUser()` で誰が開いているか分かった。
Hub は**公開のページ**なので、それができない。

代わりに、ページで Google のサインインをして受け取った ID トークンを中継に添える。
中継はそれを Google に確かめ、社内ドメインでなければ何もしない。
その「サインインの名札」が OAuth クライアントID で、GCP で一度だけ作る。
**秘密ではない**（ページに書いてよい）。手順は `tools/fm-relay/設置手順.md` の ③。

`WEB_CLIENT_ID` をスクリプトプロパティに入れると、`aud` も確かめる。
これが無いと、社員が**別のサイトでもらったトークン**でも中継を通れてしまう。

#### 先に枠だけで載せた（2026-09-10 実施・確認済み）

OAuth の設定を待たずに Hub へ載せる道があった。
**Apps Script が配る画面を、Hub のページの中に枠で埋める。**

```
Hub の 案件管理 →「🗄 FileMaker 受注入力」
  └ tools/fm-juchu-embed.html   枠（Hub の見た目・戻る・別ウィンドウ）
      └ Apps Script の /exec    中身（社内アカウントでないと開けない）
```

`doGet` に `setXFrameOptionsMode(ALLOWALL)` が入っているので枠に入る。
鍵は Hub 側に一切置かない。**設定はゼロ。**

ブラウザで通しで確認した（2026-09-10）:

| | |
|---|---|
| 枠の中に画面が出る | ○ |
| 中の JS が動く | ○ |
| 中継まで届く | ○ |
| FileMaker まで往復する | ○（存在しない番号で「見つかりません」が返った） |

サインインしていない・他サイトの Cookie を止めているブラウザでは枠に出せないので、
9秒待って「別ウィンドウで開いてください」の案内に切り替える。

③ が済んだら `fm-juchu-embed.html` の `中身` を `'fm-juchu-hub.html'` に変えるだけで、
枠はそのままに Hub 本体へ移る。

#### 切り替えの順番（大事）

ウェブアプリのアクセス設定を「全員」に変えると、**Apps Script が配る版は動かなくなる**
（誰が開いているか分からなくなるため）。
Hub 版が動くのを確かめてから切り替える。逆にすると、どちらも使えない時間ができる。

## 進め方の方針（2026-09-08 決定）

**本番環境で、少しずつ、毎日効くように進める。**

別環境（開発用の複製ファイル）は作らない。理由は2つ。

1. FileMaker には変更をマージする仕組みがない。別環境が長生きするほど合流が苦しくなる
2. まとめて公開すると変更が多すぎて、説明が必要になり、現場がついてこられない

**社員のITリテラシーを前提に、「説明しなくても分かる」改善だけを積む。**
ボタンの名前どおりに動く、勝手に初期値が入る、といった形にする。
覚え直しが必要な改善は、それ自体を設計し直す。

### 大胆な試みは Hub 側でやる

FileMaker は戻す手段が弱い。git で完全に戻せる Hub 側で試し、
定着したものだけを FileMaker に持ち込む。Hub で作ったものは移行先にそのまま残る。

## 作業の決まりごと

**① 変更は追加だけ**

既存の項目・レイアウト・計算式は変更しない。新しく足す。
どうしても既存を変える必要が出たら、この台帳に理由と元の定義を残す。

**② 変更前に必ずスナップショット**

```
fm-snapshot.cmd --note "○○を追加する前"
```

変更後にもう一度取り、`fm-snapshot.cmd --diff` で差分を確認する。
意図しない変更が混ざっていないかは、これで機械的に分かる。

**③ 1回に1つ**

複数を同時に変更しない。変更 → 照合 → 次。

**④ 新規レイアウトは `Hub` を頭に付ける**

既存レイアウトと混ざらないようにする。（例: `Hub連携`, `Hub連携_検証`）

**⑤ ルールは必ず両側に実装し、突合で証明する**

FileMaker 側の計算と Python 側の実装が同じ結果になることを、
実データ数千件で照合してから「完了」とする。

## 安全網

| 層 | 内容 | 復元できるもの |
|---|---|---|
| 1 | FileMaker Cloud の自動バックアップ | ファイル全体（要・管理コンソール） |
| 2 | 設計スナップショット（`fm_snapshot.py`） | 何が変わったかの特定。戻す手順の根拠 |
| 3 | 台帳の「戻し方」欄 | 個々の変更の取り消し |

**層2・層3は「何を戻せばよいか」を確定させるもので、自動では戻しません。**
ファイル全体の復元が要る事態には層1が必要です。

### 002. 配送有無・梱包有無

| | |
|---|---|
| 日付 | 2026-09-09 |
| 目的 | 配送・梱包が無い案件で、金額が自動で入ってしまうのを防ぐ |
| 種別 | 項目追加＋計算式の条件追加 |

**分かったこと**

「箱数 × 単価」の計算は**既に実装済み**だった。足りなかったのは有無の判定だけ。

```
配送代（変更前） = If ( not(箱数 = 0 or 箱数="") ; 箱数 * 設定配送代 )
梱包代（変更前） = If ( not(箱数 = 0 or 箱数="") ; 箱数 * 設定梱包代 )
梱包・配送代     = 梱包代 + 配送代
合計金額         = Sum ( 用紙代;印刷代;版代;加工賃;梱包代;配送代;人件費;外注データ::外注合計 )
```

**FileMaker 側**

- `受注データ` に `配送有無` `梱包有無`（テキスト）を追加。811 → 813 項目

```
配送代 = If ( 配送有無 = "無" ; 0 ; If ( not(箱数 = 0 or 箱数="") ; 箱数 * 設定配送代) )
梱包代 = If ( 梱包有無 = "無" ; 0 ; If ( not(箱数 = 0 or 箱数="") ; 箱数 * 設定梱包代) )
```

**「有のとき計算する」ではなく「無のとき0にする」**のが要点。
過去のレコードは有無が空欄なので「無」に該当せず、従来の計算がそのまま動く。
日付での切り分けが不要になった。

**単価**

`設定配送代` = 500 / `設定梱包代` = 250（自動入力）。**変更していない。**
自動入力は新規レコードにしか効かないため、過去の値は保持される。

**照合**

全期間から1,400件を抽出し、`梱包代` `梱包・配送代` `合計金額` `利益金額` を
変更前の書き出しと比較 → **不一致 0 件**。過去の金額は変わっていない。

**残作業**

- レイアウトへの配置（`配送有無` `梱包有無` を ○無 ○有 で置く）
- `カートン型式` の値一覧（クラフト / A式 / B式 / C式 / D式 / PP袋 / 名刺プラケース / 名刺紙ケース）

**戻し方**

1. 2つの式から `If ( ○○有無 = "無" ; 0 ; ` と末尾の `)` を外す
2. `配送有無` `梱包有無` を削除

**反省**

単価を 配送250 / 梱包500 と取り違えて `設定配送代` を書き換えかけた。
正しくは 配送500 / 梱包250。**既存の値を変える前に、それが現状どうなっているかを
必ず読み、思い込みで上書きしない。**

### 003. 受注伝票出力の一括チェック

| | |
|---|---|
| 日付 | 2026-09-09 |
| 目的 | 印刷する伝票を1件ずつ「レ」と打っていたのをやめる |
| 種別 | スクリプト追加（トキワ印刷AP） |
| 場所 | メニュー > 受注伝票出力（レイアウト `受注一覧　伝票`） |

**分かったこと**

左端の欄は `受注データ::伝票チェック`（フィールドID 548）。チェック印は **「レ」**。
既存の `伝票印刷(新)` が、印刷後にこの欄を全置換で空にし、`伝票作成区分` に "済" を入れていた。
つまり仕組みは既にあり、足りなかったのは**まとめて付ける手段**だけだった。

**追加したスクリプト（2本）**

```
チェックをまとめて付ける
  1 カスタムダイアログを表示 ["まとめてチェックを付ける"; …件数を出す…; 付ける / やめる]
  2 If [ Get ( 最終メッセージ選択 ) ≠ 1 ]
  3   現在のスクリプト終了
  4 End If
  5 フィールド内容の全置換 [ダイアログあり:オフ; 受注データ::伝票チェック; "レ"]

チェックをまとめて消す      … 5 の値が "" になるだけ
```

対象は**いま画面に出ている対象レコード**。ダイアログに件数を出し、
「やめる」で何もせず終わる。全件表示のまま押しても、件数を見て止められる。

どちらも「スクリプトメニューに表示」をオンにしてあるので、
**レイアウトに手を入れずに** メニューバーの スクリプト から使える。
ボタンを置きたくなったら、あとから置けばよい。

**使い方**

```
受注伝票出力 → （必要なら検索モードでしぼり込む）
  → スクリプト > チェックをまとめて付ける → 付ける
  → 印刷(新)
```

**テスト（2026-09-09）**

伝票番号 `a104362` だけの対象レコード（1件）を作って実行。

| | 結果 |
|---|---|
| 付ける | ダイアログに「1 件」と出る → レ が付いた |
| 消す | ダイアログに「1 件」と出る → レ が消えた |
| 既存のチェック | `a103913` `a104299` の レ は無傷 |
| 対象レコード | 34件の状態に復帰させた |

テスト用の一時スクリプトは削除済み。

**戻し方**

スクリプトワークスペースで2本を選んで削除するだけ。
既存のスクリプト・レイアウト・フィールドには何も触れていない。

**分かった道具（今後のため）**

FileMaker のスクリプトステップは、クリップボード形式 `Mac-XMSS` を通して

**考え方**

FileMaker の一覧には行の複数選択そのものが無い。
そこで「クリックした行番号を覚えておき、次に Shift を押しながら
クリックされたら、その間を同じ値で埋める」という形で再現する。

`Get ( ActiveModifierKeys )` の 1 のビットが Shift。

**追加したもの**

| | |
|---|---|
| 値一覧 `レ点` | カスタム値。中身は `レ` 1つ |
| スクリプト `レ点クリック（トリガ用）` | 23ステップ。スクリプトメニューには出さない |

```
$$レ点_前回       … 前にクリックした行番号
$$レ点_目印       … Get(レイアウト名) & "/" & Get(対象レコード数)
```

**目印**が要点。検索をやり直して対象レコードが変わったあとに Shift+クリックすると、
古い行番号を基準にして無関係な伝票にレが付いてしまう。

|---|---|
| `範囲① ここから` | いまの行を範囲の開始として覚える（$$レ点_開始） |
| `範囲② ここまでにﾚを付ける` | ①の行からいまの行までに ﾚ を入れる |

```
開始したい行をクリック → スクリプト >「範囲① ここから」
終わりの行をクリック   → スクリプト >「範囲② ここまでにﾚを付ける」→ 付ける
```

②は件数を出して確認してから書き込む。検索をやり直すと $$レ点_目印 が変わるので、
①からやり直すよう促す。古い行番号で無関係な伝票に付くことはない。

**テスト（2026-09-09）**

```
→ 付ける → a105258 / a105259 / a105533 / a105838 / a105858 / a106350 の6件に ﾚ
```

範囲外の行は変わらなかった。

**`レ点クリック（トリガ用）` の扱い**

削除せず、本来の形（Shift 範囲処理）に戻して残してある。
いまは発火しないので無害。将来グループを解除すれば、そのまま Shift 方式が使える。

**分かったこと**

- FileMaker の一覧に行の複数選択は無い。範囲は「開始を覚えて、終わりで埋める」で作る
- **ボタングループの中の部品はスクリプトトリガが効かない**。トリガが動かないときは、
  まず先頭に無条件のダイアログを置いて「そもそも発火しているか」を確かめる

```
$$レ点_前回 = $今 / $$レ点_目印 = レイアウト名 & "/" & 対象レコード数
```

### 009. 見積と受注を同じ器に置く（設計と、項目の追加）

| | |
|---|---|
| 日付 | 2026-09-10 |
| 種別 | 項目追加（受注データ 814 → 817）＋ Hub受注 レイアウトへの配置 |

**決めた形**

見積と受注は同じ情報なので、`受注データ` に同居させる。段階ごとに1レコードを残す。

```
案件（同じ製品の系列・案件ID で束ねる）
 ├ 2026 予算見積      金額感の基準として残る
 ├ 2026 見積          ここで変わった点
 └ 2026 受注          さらに変わった点（実際に作った内容）
        ↓
 └ 2027 予算見積      内容は「最新＝2026受注」から流し込む
                      金額は「前回の同じ段階＝2026予算見積」を横に並べる
```

**鎖は案件につき一本にする。** 段階ごとに鎖を分けると、予算見積の鎖だけが
受注時の変更を知らないまま伸びていく（本多さんの指摘: 予算見積=両面カラー、
受注=片面カラーのまま翌年両面カラーで見積を出してしまう）。

そのため:

- 種は常に「同じ案件IDのうち起票日がいちばん新しい1件」に固定する
- **段階を選んで種にする操作は作らない**（作れば必ず間違える）
- 前回の同じ段階は**流し込まず、金額を横に並べるだけ**
- 新規に起こした瞬間に「前の段階から変わっているところ」を警告として出す

**足した項目（3つ・追加のみ）**

| 項目 | 中身 |
|---|---|
| `案件区分` | 予算見積 / 見積 / 受注 / 失注。空欄は従来の受注レコード |
| `案件ID` | 同じ案件の系列を束ねる識別子 |
| `見積番号` | 見積段階の番号。受注化して初めて伝票番号を採る |

`Hub受注` レイアウトには、さらに `伝票作成区分` `納品書作成区分` を載せた
（見積を既存業務から外すために書く必要があるため）。267項目・0.17秒のまま。

**監査でわかったこと（376本のスクリプトを XML で一括取得して調査）**

受注データを絞っている条件は、これだけだった。

| 条件 | どこで |
|---|---|
| `伝票作成区分 = 未` | 受注伝票出力 |
| `伝票チェック = ﾚ` | 伝票印刷（新・保存・2階用・2） |
| `納品書チェック = ﾚ` | 納品書作成（4本） |
| 除外 `納品書作成区分 = 済` | 納品書出力 |
| `起票日 2021〜2030` | 工程管理 検索 |

**全レコードを表示** を使うもののうち、受注データを見ているのは
`得意先別売上高推移エクスポート`（レイアウト 受注データA）の1本だけ。
ここに見積が混ざると売上が狂う。

### 011. 段階と番号の決まり

| | |
|---|---|
| 日付 | 2026-09-10 |
| 種別 | 採番規則の決定と、中継への実装 |

**既存の採番のしくみ（調べて分かったこと）**

`伝票番号` は自動採番ではない（`autoEnter: false`）。自動なのは `no` のほうで、
`受注データ新規作成` スクリプトがこうしていた。

```
新規レコード/検索条件
フィールド設定 [ 伝票番号 = 受注データ::no ]
```

つまり「`no` の自動採番を伝票番号に写す」のが実態。**この仕組みをそのまま使う。**

**決めた形（後ろ付け・2026-09-10 決定）**

```
新規レコード      no が a108193 で自動採番される
案件ID           a108193              ← no をそのまま案件番号にする
予算見積          見積番号 = a108193-YM01、2件目は -YM02
見積             見積番号 = a108193-M01、 2件目は -M02
受注             伝票番号 = a108193     （＝案件ID。今までと同じ形）
失注             番号はそのまま、案件区分だけ変える
```

見積レコードの `no` は空にする。受注化したときに **伝票番号 = no = 案件ID** という
今までの形が保てるようにするため。番号も無駄にならない。

**なぜ後ろ付けか**

| | |
|---|---|
| 並べたとき | 同じ案件が固まる。前付けだと種類ごとに固まり案件が散らばる |
| 既存の決まり | 分割納品で `a090903-A` `-B` を使っている。同じ欄に前付けと後ろ付けを混在させない |
| 書類の読み | 「見積番号: a108193-M01」のほうが、先頭が毎回変わらず探しやすい |

`a` は後で変えられるよう、記号の組み立ては `段階` の一箇所にまとめてある。

**中継に実装したもの**

| 関数 | |
|---|---|
| `画面_新規案件(種別, 初期値)` | まっさらな案件を起こす。`no` を案件IDにして採番する |
| `画面_新規段階(案件ID, 種別)` | 次の段階を起こす。**種は常にその案件の最新1件** |
| `次の番号_` | 同じ案件・同じ段階の件数から `-YM01` `-M02` を作る |
| `最新_` | 起票日 → recordId の順で新しい1件 |
| `同じ段階の前回_` | 前年の予算見積など、参考として並べる相手 |
| `差分_` | 2つのレコードで中身が違う項目を並べる |

`画面_新規段階` は、**種（最新）**と**参考（前回の同じ段階）**と**その差分**を一緒に返す。
翌年の予算見積を起こしたとき、内容は受注時の変更込みで入り、金額は前年の予算見積を
横に並べ、変わっているところを警告として出せる。

**引き継がないもの**

`伝票番号` `見積番号` `案件区分` `案件ID` `no` `伝票作成区分` `納品書作成区分`
`伝票チェック` `納品書チェック` `起票日` `納品日` `注残数`

`Hub受注`（表示・編集用・262項目）と役割を分けた。
